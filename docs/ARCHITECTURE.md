# 代码架构

DocAtlas 要同时服务多个版本、多个产品、多个文档站，所以有一条硬规矩：

> **核心代码不认识任何具体网站，也不认识任何具体技术领域。**

站点特有的东西（域名、接口格式、URL 规则）住在**来源适配器**里，
领域特有的东西（Unreal 的 `K2_` 前缀、蓝图和 C++ 的对应关系）住在**领域知识包**里。
这样加一个版本只改配置，加一个站点只加一个文件，不用改遍全库。

---

## 三层分工

```
┌─────────────────────────────────────────────────────────────┐
│ 核心 docatlas/*.py                                          │
│   HTTP 限速、SQLite、切块、检索、上下文预算、CLI            │
│   不知道 Epic 是谁，也不知道 Unreal 是什么                  │
└────────────────┬────────────────────────┬───────────────────┘
                 │                        │
      ┌──────────▼──────────┐  ┌──────────▼──────────────────┐
      │ sources/<name>.py   │  │ knowledge/<name>.py         │
      │ 懂一个**站点**       │  │ 懂一个**领域**（可选）       │
      │ 怎么列页 / 怎么解析  │  │ 别名规则 / 交叉推断          │
      └─────────────────────┘  └─────────────────────────────┘
                 ▲                        ▲
                 └────────┬───────────────┘
                  datasets/*.toml
                  纯数据：网址、分类、实体类型、检索权重
```

**依赖方向只能向下。** 核心不得 import 具体的 `sources.epic_ue` 或
`knowledge.unreal`——它只通过 `config.SOURCE` / `config.KNOWLEDGE` 拿到
运行时选中的那一个。

### 为什么知识包不是抽象基类

`knowledge/unreal.py` 就是个普通模块，实现哪个函数就提供哪项能力，
核心用 `knowledge_hook()`（本质是 `getattr` + 默认值）去取。

不做抽象基类、不做注册表、不做插件框架，是因为：只有一层调用关系、
只有一个可选实现点，基类只会逼着新来的实现方写一堆空方法。
少写一个 `import` 就少一条循环依赖，也少一份要维护的样板。

### 为什么领域知识不做成配置

像"`K2_` 开头要脱前缀""`U/A/F/I/E/T` 开头是类型前缀，但只对类页成立"
"蓝图和 C++ 靠 `DisplayName` 元数据对应"这类规则，写成配置会变成一套
既难读又没法测的迷你语法。写成普通 Python 函数反而清楚，还能直接写单元测试。

**分界线**：能用键值表达的（网址、分类、权重）进 TOML；
需要条件分支和正则的（行话、推断）进知识包。

## 六个关键设计

### 1. 代码和数据分开住

`config.py` 里 `REPO_ROOT` 是代码根，`DATA_ROOT` 是数据根，两者无关：

```
DOCATLAS_HOME     数据放哪（默认 <仓库>/data）
DOCATLAS_DATASET  用哪个数据集（不设内置默认，见 .docatlas-local.toml）
```

一个数据集独占一个目录、一个 SQLite。**刻意不合并成大库**：
删除、备份、故障隔离都简单得多，也不会有一个库越长越大的问题。

跨数据集查询就是"依次查再合并"，不搞联合视图。

### 2. 抓取速度：自适应，不写死

官网会限流，阈值没有公开。所以 `net.GlobalRateLimiter` 用 AIMD
（和 TCP 拥塞控制同一套思路）自己找上限：

- 连续成功 12 次 → 速率 +0.3 请求/秒（上限 10，实测就在这附近）
- 撞上 429/403 → 速率 ×0.75，并全局冷却（首次 4 秒，短时间内反复被拒才加长）

关键细节：**一次限流事件只降一档**。一次限流会让所有在途请求同时失败，
如果每个失败都降速，速率会瞬间跌到地板再也回不来——第一版就是这么慢到
0.5 页/秒的。`penalize()` 里用"是否已在冷却中"来识别是不是同一次事件。

### 3. 切块：先攒小的，再切大的

按标题切出来的小节里，有大量像 `Inputs` 这种只有一行表头的段落。
单独成块的话一块只有二三十个 token，既答不了问题又占检索名额。

所以切块分三步（`chunking.chunk_sections`）：

1. **攒**：同一个父标题下相邻的小段落合并到目标大小（子标题保留在正文里）
2. **切**：本来就超标的大段落按表格 / 代码围栏 / 列表的边界切开
3. **收尾**：切剩的一小截并回上一块，不留孤块

**不要按小节的标题名判断它有没有用。** Epic 蓝图页的 `Navigation` 小节，
名字像面包屑，实际上除了面包屑还装着"这个节点是干嘛的"和 `Target is X`——
全页最有用的信息都在里面。所以这类小节照常合并，只是**不由它决定合并块的
类型**（`WEAK_TYPE_LABELS`）：一块含着描述、参数和返回值的内容如果被标成
"导航"，检索时会被一路扣分扣到底。

实测效果：被切碎的页面 7,860 → 76，平均块大小 143 → 273 token，
不到 50 token 的碎块从 54.6% 降到 5.2%，总块数少 47%（索引跟着瘦）。

**改块的边界，会打断在别处靠边界吃饭的代码。** 知识包里认 `Target is X` 的
正则，原来用"字符串结尾"给类型名收边——它一直能用，靠的是"这句正好是小节
最后一句"这个从没写下来的前提。合并之后名字后面直接接下一段正文，中间连个
标点都没有，命中数当场从 1,336 掉到 4。现在改成拿候选名去别名表里对
（`unreal._resolve_target_entity`），边界由数据说了算，跟切到哪儿无关。

### 4. 加工数据要能自证出身

`pages.parser_version` 和 `chunks.parser_version` 记录每一份加工结果
是由哪版切分规则产出的。这解决两个问题：

- **中途换规则不会新旧混杂而无法区分**——能精确查出哪些还没升级
- **`reprocess` 变成可续传的**——默认只做未升级的页，断掉再跑就是接着做

改切分规则时，把 `constants.CHUNKER_VERSION` 加一，然后跑 `reprocess`。

### 5. 检索的连接顺序不能交给优化器

`chunks_fts` 是 FTS5 虚表。`WHERE chunks_fts MATCH ?` 只有在**全文索引当外层
循环**时才是索引查询；一旦优化器决定先走别的索引（带 `--category` 时它就会
从 `idx_pages_category` 出发），`MATCH` 就退化成"每个候选行单独跑一次全文
匹配"。同一条查询的实测差距是 **0.05 秒 vs 44 秒**，而且完全没有报错——只是
慢，慢到外层超时把它杀掉。

所以 `search.py` 里的全文查询一律写成：

```sql
FROM chunks_fts
CROSS JOIN chunks c ON c.id=chunks_fts.rowid
CROSS JOIN pages  p ON p.id=c.page_id
WHERE chunks_fts MATCH ? AND p.category=?
```

`CROSS JOIN` 在 SQLite 里的语义就是"不许重排这两张表的顺序"。同理，
`名称=? OR 别名=?` 这种跨两张表的 OR 也会让优化器整个放弃索引，
`_entity_hits` 因此写成 `UNION` 的两条分支。

### 6. 上下文保护：硬预算

`context.py` 是 `ask` / `related` 的**唯一实现**，命令行和 MCP 都调它——
以前两边各写一套"要不要补抓"的判断，然后慢慢分了岔。上下文包的四条规则：

1. 累计 token 超预算就停，**不存在"最后一条超一点没关系"**
2. 一个页面最多贡献 2 块
3. 内容哈希相同的块只留一份
4. 一跳交叉关系**只给指针**（名称、依据、置信度、展开命令），不塞正文

输出用 Markdown 而不是 JSON —— 同样内容省 30~40% token。

**不做上下文重叠**：重叠会让 `content_hash` 失去唯一性，直接破坏第 3 条去重，
还会把全文索引撑大 20~30%。需要相邻内容时顺着 `prev_chunk_id` / `next_chunk_id` 取。

## 测试

```powershell
python -m unittest discover -s tests -v
```

128 个用例，全部离线，覆盖：知识块大小上限、小节合并与孤块回收、
代码围栏切分后仍配对、别名生成、标题锚点不吞链接地址、行内 HTML 清理
（且不破坏 C++ 模板尖括号）、检索档位阶梯与查询形状判定、限速器 AIMD 行为、
限流与真失败的区分、302 重定向的特殊处理、按需抓取的三档定位，
以及"落库 → 检索 → 上下文包"的端到端流程（含预算不越界断言）。

还有几组用例专门守边界：

- **守分层**：配置出错要给出可行动的提示、适配器地址必须跟着数据集版本走、
  **没挂知识包时一切照常工作**、输出里不许再出现写死的产品名。
- **守验收**：空库和空分类必须验收失败——"没有不合格的行"不等于"有数据"。
- **守配额**：`--sample-per-category` 是每类上限，短分类的缺额不许转给别的类。
- **守清单来源**：适配器换掉 `inventory_feeds` / `read_feed` 之后，
  落库字段、失败诊断和验收结果都要和 sitemap 路径一模一样。
- **守 MCP 协议**：握手要回声客户端版本、通知不能回响应、工具异常要变成
  isError 结果而不是搞崩连接、**读到的每个参数都必须写进 inputSchema**。
- **守 CLI 与 MCP 一致**：两边的 `ask` 必须调同一个 `context.answer()`，
  各写一套"要不要补抓"的判断迟早会给出不一样的答案。
- **守"能不能跑起来"**：**包里每个模块都必须能被 import**、
  每个子命令都得绑上处理函数、技能文档里写的命令和工具都必须真实存在。

最后这组是补出来的：`cli.py` 里曾经有个 f-string 语法错误，
当时全部用例都是绿的——因为没有一个测试 import 过它。
测得再细，也补不上没测到的那一块。

测试把 `DOCATLAS_HOME` 指到临时目录，**不会碰真实知识库**；
数据集则用真实的那一份配置，所以 `datasets/*.toml` 本身也在覆盖范围内。
