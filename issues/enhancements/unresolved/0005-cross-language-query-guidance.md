# 背景

DocAtlas 是面向原始技术文档的确定性检索层，不负责理解和翻译用户语言。用户使用
中文查询英文数据集时，应由位于用户与 DocAtlas 之间的 AI/Skill 把问题转换成可靠的
英文检索词，再调用 DocAtlas；不应要求普通用户自己猜英文术语，也不应把开放式翻译
逻辑塞进 DocAtlas 核心。

核心已经能够在空结果时报告书写系统不匹配。该诊断是给 AI 读取的结构化信号，
不是最终用户需要亲自处理的工作。

本轮固定版本测试中：

- Shader 中文“渐变条/把灰度花纹重新映射成颜色”的多种问法与中文 `search`
  稳定为空；英文 `Color Ramp Node Mix Color Node Noise Texture` 立即命中目标页。
- Geometry 中文“把小方块撒到网格表面并朝向法线”主智能体复现为
  206 ms、退出码 1、0 结果；同义英文控制查询 208 ms、退出码 0，返回 17 个知识块，
  前两位包括 Mesh Sample Nodes 与 Distribute Points on Faces。
- C++ 中文 variant/optional 问题会召回无关 C 文档；即使英文自然改写仍受排序问题
  影响，但精确英文符号至少能进入相关候选。

# 目标

- AI/Skill 读取数据集声明语言，并把用户问题转换为该语言的检索词。
- 保留代码符号、版本号和专有名词，避免翻译破坏技术含义。
- 首次查询弱相关或返回 `language_mismatch` 时，由 AI 自动生成更准确的官方术语
  重试，并把最终答案用用户的语言解释。
- DocAtlas 核心只提供数据集语言、查询状态、来源和检索结果，不承担开放式翻译。

# 可能方向

- 在 DocAtlas Skill 中规定“读取数据集语言 → 生成原文术语 → 查询 → 必要时改写重试”
  的固定流程。
- 查询改写只影响检索词，不篡改、翻译或伪造 DocAtlas 返回的官方来源。
- AI 最终可用用户语言解释结果，但引用仍指向原始文档。

# 待讨论问题

- 查询翻译怎样在上层 Skill 中保持可审计，并把原查询和重试词一并记录？
- 如何避免错误翻译专有名词后补抓无关页面？
- 对非拉丁文字的语言检测需要做到什么精度才值得维护？

# 非目标

- 不要求把英文官方正文自动翻译成中文。
- 不把指定来源本身缺少中文版本判定为产品错误。
- 不在 DocAtlas 核心实现通用机器翻译或自然语言理解。
- 不在本议题中调整英文查询的排名；该问题由 `BUG-002` 跟踪。

## 2026-07-26 补充调查

重建 `cppreference-2026-07-26` 后，中英混合查询暴露了现有诊断的边界：

- 第一种中文 variant 描述约 218 ms，状态为 `ok`，但首条是泛化的 C++20 页面。
- 改写后的中文约 190 ms，首条才落到 `std::variant` 构造函数。
- 英文精确查询
  `std::variant<int, std::string> std::holds_alternative std::get C++20`
  约 1266 ms，并触发 1 页补抓。

目前 `language_mismatch` 只在空结果时出现；只要异语言查询碰巧返回弱相关内容，
诊断就会被 `ok` 掩盖。后续判断应同时考虑首条相关度和书写系统差异，而不只看
结果是否为空。

# 验证思路

使用本轮三条固定控制组：

1. Blender Shader：中文 Color Ramp 自然问法 / 英文官方节点名。
2. Blender Geometry：中文散布并朝向法线 / 英文 Distribute + Align 问法。
3. cppreference：中文 variant/optional / 英文精确标准符号。

验证 AI/Skill 能读取数据集语言，把中文问题改写成保留技术符号的英文查询，并在
首次结果弱相关时自动重试。最终回答应使用用户语言，引用应保持为英文原始文档；
同时确认 DocAtlas 核心不承担翻译，也不因这层改写而放宽补抓规则。

## 历史验证：核心诊断已具备

下面记录的是先前完成的核心诊断能力，不代表当前 AI/Skill 查询翻译目标已经完成：

| 目标 | 状态 |
|---|---|
| 查询语言与数据集语言明显不一致时给出结构化信号 | 已做 |
| AI/Skill 自动查询翻译与重试 | **未做** |
| 区分"异语言未命中"与其他几种"没有" | 已做，五种状态各有各的下一步 |

`CrossLanguageDiagnosisTests` 用议题的三条控制组形状钉死行为：

```text
script_mismatch("如何设置视野", "en-US")      -> "han"    （异语言）
script_mismatch("如何设置视野", "zh-CN")      -> ""       （同语言，不报）
script_mismatch("Set Field Of View", "zh-CN") -> "latin"  （反过来也成立）
script_mismatch("ノードの設定", "ja-JP")      -> ""       （汉字假名混写不误判）
script_mismatch("K2_SetTimer", "en-US")       -> ""       （纯符号不报）
```

同一条中文查询，在英文库里报异语言、在中文库里不报——**语言取自数据集的
`language` 字段，不是对用户的假设**。

空结果的措辞实测：中文问句得到"这个库的正文是 en-US（拉丁字母），而这条查询
是用汉字写的，所以必然一条都对不上——不是官方没有这一页"，并给出改写建议；
同一个库里查 `zzzznotarealpage` 仍然得到"官方文档确实没有这一页"。
两者不会互相串味。

MCP 的 `docatlas_ask` 相应给出独立状态 `language_mismatch`。

## 历史实现记录

**核心做了诊断，但 AI/Skill 查询改写尚未实现。**

议题的目标写的是"当查询语言与数据集声明语言明显不一致时，提供可理解、
可执行的下一步"，并在验证思路里明确给了"**或至少**返回明确的语言不匹配诊断
与可执行下一步"这条退路。落地的就是这条。

**改动**：

- `text.dominant_script()` / `expected_scripts()` / `script_mismatch()`：
  按 Unicode 区段认书写系统。这里回答的是"用什么字写的"，不是"说的是哪国话"。
  语言标签 → 书写系统是一张小表（`zh→汉字`、`ja→假名+汉字`、`ru→西里尔`…），
  那是书写系统的事实，不是对用户的假设。
- 只在**空结果**时才说。有结果时闭嘴——符号和代码本来就不翻译，
  用拉丁字母查中文库照样能命中。
- 不认识的语言标签退回拉丁字母，不报错。

**为什么不做查询改写**：议题的非目标写着"不要求把英文官方正文自动翻译成
中文"，可能方向里也把改写层列为"可审计的、只改检索词"的可选项。真要做，
风险在议题里已经点明——"如何避免错误翻译专有名词后补抓无关页面"。
在没有术语表、也没有那两个小样数据集可验证的情况下，猜着翻译会把
"补抓 5 页"变成"补抓 5 页错的"。

分工按议题"待讨论问题"的第一条定：**改写属于上层 Skill**。核心负责如实
指出"你用的字和这个库不是一套"，AI 拿到这条诊断后自己落成原文术语再查一次
——它本来就会这件事，而且比一张静态别名表准。`SKILL.md` 的"查不到怎么办"
已经把五种"没有"和各自的下一步写成表格。

**仍未做**：中文自然问句直接命中英文页面。需要术语表或改写层，且必须先重建
`blender-manual-5.2` / `cppreference-2026-07-26` 才能按议题的三条控制组验证。
